FIRST SIGN-IN
{{- if .Values.admin.existingPasswordSecret }}
  The first administrator "admin" takes its password from Secret {{ .Values.admin.existingPasswordSecret }} (key {{ .Values.admin.existingPasswordSecretKey }}),
  on a fresh database only. If the data volume already had users, that password is ignored and the existing accounts apply.
{{- else }}
  On a fresh database the server generates a one-time password for the user "admin" and prints it to its log, once:
    kubectl -n {{ $ns }} logs deployment/{{ $fn }} | grep -A2 'First start'
  You choose a new password at first sign-in. If the line is missing, the database already existed: see "Recovery" in deploy/README.md.

  Registration is "{{ .Values.registration }}"{{ if eq .Values.registration "open" }}: ANYONE who can reach the admin address can create an account and an organization. The first administrator can invite them.{{ else }}: nobody can register; accounts are made with `server create-org` / `server reset-password` (kubectl exec).{{ end }}

CONNECT A CLUSTER
  Open "Connect a cluster" in the UI; it prints the complete `helm install` for the agent (server address, CA pin, token).
  The CA pin the agent trusts is also in the server log:
    kubectl -n {{ $ns }} logs deployment/{{ $fn }} | grep -o 'ca_pin=[^ ]*'
  or from the API, once you have signed in in the UI and chosen your own password (the API refuses everything before that; the
  session cookie is kept in ./jar; the org id is "{{ .Values.org }}"):
    UI={{ if .Values.httproute.enabled }}{{ with (first .Values.httproute.hostnames) }}https://{{ . }}{{ end }}{{ else }}http://localhost:{{ .Values.admin.service.port }}{{ end }}
    curl -sc jar -H 'X-Requested-With: curl' -H 'Content-Type: application/json' -d '{"username":"admin","password":"..."}' $UI/api/v1/auth/login
    curl -sb jar $UI/api/v1/orgs/{{ .Values.org }}/info | jq -r .caPin
  If you keep the chart for the agent locally, the server also serves it (unauthenticated): curl -O $UI/charts/<file shown in the UI>.

CA KEY PASSPHRASE
  --ca-key-passphrase-file is passed (Secret {{ .Values.pki.caKeyPassphraseSecret.name }}, your own). The server build must support that flag, and the
  passphrase must be backed up separately from the data: without it a backup of the CA key is useless.
{{- else if .Values.pki.encryptAtRest }}

CA KEY PASSPHRASE
  pki.encryptAtRest is true (the default): this chart generated its own passphrase into Secret {{ include "continuum.caPassphraseSecretName" . }} and
  the CA private key is encrypted under it. Back that Secret up separately from the data volume: without it a backup of the CA key is useless, exactly
  like the key itself (deploy/README.md, "Encrypting the CA key at rest").
{{- else }}

CA KEY PASSPHRASE
  pki.encryptAtRest is false: the CA private key is stored UNENCRYPTED on disk. Anyone who reads it, or a backup of
  it, can issue certificates every agent would trust. Only turn this off for local/dev use or where disk-level
  encryption already covers it.
{{- end }}
