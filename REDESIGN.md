# The redesign: where the plan is and where we are

This file exists so the plan is not lost between sessions. It points at the plan and keeps a short status. Update the status at each gate, in the same commit as the work.

## The plan to follow

**Ikhnos: the plan to follow** (https://claude.ai/artifact/8vfoZWCoq5acknQixSX9UK). One page that merges the two documents below: the target, what is being fixed, the order of stages with their gates, where we are, and the decisions taken and open. Read it first. It is the plan.

It is built from two documents, which stay as the reasoning and the evidence:

1. **Ikhnos architecture: control plane, data plane and the seams between** (https://claude.ai/artifact/UwySnmbgattPpNxM1mTmaV). The first document: the target shape, ten seams, six contracts, a strangler migration.
2. **Ikhnos design: entities, interfaces and channels, from the code** (https://claude.ai/artifact/W1FoXitwyaUmXsZS9CwxaM). A second pass over the first, made against the code and reviewed. It holds the defects D1 to D14, the smaller plan with its stop line, and a progress log.

Where the two differ, the second pass wins.

## Rules that hold throughout

- A phase may delete code, move code or add a contract. It does not add a user feature. Features resume after the stop line.
- Each change is its own commit, with a test that fails without it, a rollback plan and a compatibility plan.
- The stop line asked that the minimal decision loop run in production before anything below it starts. That gate was waived on 2026-10-17, because there is no advisor yet to run it; work that does not depend on what the loop would show goes ahead, one small commit at a time.
- The first three stages change no wire format except one additive protocol change.

## After the plan: what an audit against the code found (2026-10-23)

The three documents were read in full and measured against the repository. The structure the plan asked for is in place (the server package is about 2,000 lines of wiring, 21 packages hold an import rule, no cross-module use is listed, every route and every store method's organisation scope is pinned). What was promised and is not built, in the order it is worth doing:

1. This file and the plan page say what the code says (done in this change). CI runs the Neo4j tests, the real-collector tests and the helm renderings it used to skip, and fails when a tool it relies on is missing (`CONTINUUM_REQUIRE_TOOLS`, done in the change after this one).
2. Done (the change after the CI one): fuzz tests for what arrives from outside (capability names, the PROXY header, a sync, a series of chunks, a flow batch, the install renderer against a real shell) and a fake agent that can send any message, replay, reorder and say what ended a stream, with five scenarios across streams. Nothing was found: the seeds run with every `go test`, and each target was fuzzed for a minute or more. Not done: a scheduled fuzz run in CI, which is worth adding the first time a target finds something.
3. Done (the change after the fuzz one): a guard on the agent protocol (`internal/protocompat`). The schema of the build is compared with a committed baseline and every change an older peer would misread is named and fails; additions pass. Not done, on purpose: running the previous release's agent against the new server. There is no earlier release to run (v0.1.0 is the first commit) and the agent's tests use an in-process fake of the cluster, which an old binary cannot use; build it when a release exists and the agent can run against a fake cluster API. The baseline is refreshed at each release.
4. Done (the change after the protocol guard): the TOTP secrets, the mail password and each organisation's decider secret are sealed at rest (`internal/sealing`), under a key read from a mounted Secret file (`sealing.keySecret` in the server chart, off until a Secret is named). The server refuses to start on a database that holds sealed secrets without their key, a replaced key is put on top of the old one, and `server reset-sealing` is the way out of a lost key. The first sealing rewrites the database file, because a test that read the raw files showed SQLite leaves a replaced value in it. The audit chain is kept forever for now: it is small at tens of clusters, and a retention rule is written when a size shows it is needed. Still to do: a URI name in certificates that says whether one is an agent's or an operator's, and a written story for rotating the CA.
5. Only when Objectives starts: `Condition` moved from the agents package to the kernel; delivery receipts; a shared kit for a new kind of resource (the telemetry intents, the operators and the proposals are the examples it would be taken from).
6. Left alone on purpose: splitting the hub's one lock (nothing shows contention at tens of clusters; measure first), the four Core callbacks (they work), narrow store ports per module (done with the next module touched), server-sent events (a feature), Ikhnos's own traces and SLIs (after the first Objective).
7. Never in the plan; decided on 2026-10-23: the names (chart, image, domains) change after the hardening items above, with `continuum.v1`, the in-cluster names, selectors, the identity Secret and token prefixes kept, old and new metric names emitted side by side for a while, and the Go module left as it is; the GitOps and CRD lifecycle starts as a short design note (a values-file export first, no CRDs and no controller now). Still open: the names (chart, image, domains; `continuum.v1` and the in-cluster names stay), the GitOps and CRD lifecycle (a short design first), widening `KubeAPI` to write a rules ConfigMap, and Objectives itself (parked).
